# Ревью, CI и коммиты

## Ревью кода / PR

1. Понять цель изменений (задача, багфикс, рефакторинг).
2. Проверить: корректность логики, граничные случаи, обработку ошибок, соответствие стилю проекта, утечки секретов в код/логи.
3. Оформить замечания кратко, с приоритетом:
   - **Блокер** — нельзя мержить без исправления.
   - **Важно** — сильно желательно до merge.
   - **Замечание** — по возможности.
4. Если есть тесты — указать, покрывают ли они изменения; при отсутствии — предложить минимальные проверки вручную или тестами только если это уместно по объёму задачи.

## CI / пайплайн

1. Прочитать полный лог шага с ошибкой (не только последнюю строку).
2. Воспроизвести локально ту же команду (сборка, линтер, тесты), если в репозитории это документировано или очевидно из конфигурации.
3. Разделить: ошибка окружения, флейк, регрессия кода, конфиг CI.
4. После исправления — убедиться, что причина устранена, а не замаскирована.

## Сообщения коммитов

- Одна строка — суть; при необходимости тело с деталями (что и зачем).
- Если в проекте уже есть соглашение (Conventional Commits, префиксы задач Jira и т.д.) — **следовать ему**; иначе — нейтральный императив: «Исправить отображение даты», «Добавить проверку прав».
- Не смешивать в одном коммите несвязанные изменения; сообщение отражает фактический дифф.

## Инструменты

- Использовать `git diff`, `git log`, файлы CI в репозитории (`.github/workflows`, `gitlab-ci.yml`, `Jenkinsfile` и т.п.) по факту наличия.
- Не выдумывать имена веток и номера задач — брать из контекста пользователя или из вывода git.
